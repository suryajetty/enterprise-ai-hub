# LangChain in Production: The Hard Parts Everyone Skips

Most LangChain tutorials show you how to connect a model, create a prompt, and build a simple chain.

That is useful for learning.

But production is different.

An enterprise LangChain application has to deal with authentication, authorization, sensitive data, model failures, retries, observability, evaluation, cost, latency, versioning, and integration with existing enterprise systems.

This is where the real engineering begins.

---

## Why LangChain?

A production AI application rarely consists of only:

```text
User → LLM → Answer
```

A real enterprise workflow may look more like:

```text
User
  ↓
API Gateway
  ↓
Authentication / Authorization
  ↓
Application Service
  ↓
LangChain / LangGraph
  ↓
Retrieval / Tools / APIs
  ↓
Guardrails
  ↓
LLM
  ↓
Validation
  ↓
Response
```

LangChain provides building blocks for connecting models with prompts, tools, retrievers, structured outputs, and other application components.

The engineering challenge is not simply learning the framework.

The challenge is knowing **where LangChain belongs in the architecture**.

# The LangChain Mental Model

Before writing code, understand the basic building blocks.

```text
Model
  +
Prompt
  +
Retriever
  +
Tools
  +
Structured Output
  +
Memory / State
  +
Observability
  =
AI Application
```

LangChain is the orchestration layer connecting these components.

It should not become the entire application architecture.

---

# 1. Model Integration

The first mistake beginners make is tightly coupling their application to a single model provider.

Instead, isolate the model configuration.

For example:

```python
from langchain.chat_models import init_chat_model

model = init_chat_model(
    "openai:gpt-5.5"
)
```

The application logic should not need to know every detail about the provider.

This makes it easier to change models as business requirements evolve.

For example:

```text
Development
    ↓
Open-source model

Testing
    ↓
Cloud model

Production
    ↓
Enterprise-hosted model
```

The orchestration layer remains largely unchanged.

---

# 2. Prompt Engineering

Avoid scattering prompts throughout the codebase.

Bad:

```python
response = model.invoke(
    "Answer this question using the following context..."
)
```

Instead, maintain prompts as versioned application assets.

```python
from langchain_core.prompts import ChatPromptTemplate

prompt = ChatPromptTemplate.from_messages([
    (
        "system",
        """
        You are an enterprise AI assistant.

        Use only the supplied context.

        If the information is unavailable,
        clearly state that you do not have
        sufficient information.
        """
    ),
    (
        "human",
        "{question}"
    )
])
```

Now prompts can be:

* Version controlled
* Tested
* Reviewed
* Evaluated
* Updated independently

---

# 3. Retrieval

This is where LangChain becomes particularly useful for RAG applications.

The high-level flow is:

```text
User Question
      ↓
Retriever
      ↓
Relevant Documents
      ↓
Prompt
      ↓
LLM
      ↓
Answer
```

But production retrieval should not simply mean:

```python
retriever.invoke(question)
```

You need to consider:

* Top-K
* Metadata filtering
* Hybrid search
* Re-ranking
* Access control
* Document freshness
* Chunk quality
* Retrieval evaluation

---

# 4. Vector Database

A production application should isolate vector-store configuration from business logic.

For example:

```python
import os

from langchain_openai import AzureOpenAIEmbeddings
from langchain_milvus import Milvus

embeddings = AzureOpenAIEmbeddings(
    azure_deployment=os.getenv("AZURE_OPENAI_EMBEDDING_DEPLOYMENT"),
    api_version=os.getenv("AZURE_OPENAI_API_VERSION"),
)

vector_db = Milvus(
    embedding_function=embeddings,
    connection_args={
        "uri": os.getenv("MILVUS_URI"),
        "token": os.getenv("MILVUS_TOKEN"),
    },
    collection_name="enterprise_knowledge_base",
)
```

**Never hardcode credentials.**

The exact model deployment name, API version, and vector-store integration should be configuration-driven and validated against the versions used by your deployment.

---

# 5. Tools

This is where a simple RAG application starts becoming an agentic application.

Instead of only retrieving documents, the AI system can interact with enterprise systems.

For example:

```text
                    LangChain / LangGraph
                            │
              ┌─────────────┼─────────────┐
              ↓             ↓             ↓
          Retriever      Tool        Tool
              │             │             │
              ↓             ↓             ↓
         Knowledge DB    ServiceNow    Database
```

A user might ask:

> "What caused yesterday's production incident?"

The system may:

1. Search incident documentation.
2. Retrieve logs.
3. Query ServiceNow.
4. Search the knowledge base.
5. Correlate the evidence.
6. Generate a response.

That is significantly more powerful than a chatbot that only retrieves documents.

---

# 6. Guardrails

Never assume that the LLM will enforce enterprise security by itself.

Security controls should exist outside the model.

For example:

```text
User
 ↓
Authentication
 ↓
Authorization
 ↓
Input Validation
 ↓
LangChain
 ↓
Retriever / Tools
 ↓
LLM
 ↓
Output Validation
 ↓
User
```

Guardrails should address areas such as:

* PII
* Prompt injection
* Unauthorized data access
* Tool misuse
* Malicious input
* Unsafe output
* Sensitive information leakage

---

# 7. Observability

A production AI system needs more than application logs.

You need visibility into:

```text
Request
  ↓
Prompt
  ↓
Retriever
  ↓
Documents
  ↓
Tool Calls
  ↓
Model
  ↓
Response
```

Important metrics include:

* Latency
* Token usage
* Model cost
* Retrieval relevance
* Error rate
* Tool failures
* Response quality
* User feedback

This is where LangSmith and other observability/evaluation tooling can become part of the engineering stack.

---

# 8. Evaluation

A common mistake is:

> "The application works because I tested five questions."

That is not evaluation.

Create a representative evaluation dataset.

```text
Question
Expected Answer
Retrieved Documents
Actual Answer
Score
```

Then measure:

* Retrieval quality
* Answer correctness
* Groundedness
* Relevance
* Latency
* Cost

A production AI system should be evaluated continuously, especially when changing:

* Models
* Prompts
* Embeddings
* Chunking
* Retrieval strategy
* System instructions

---

# 9. Cost Control

An enterprise application can become expensive surprisingly quickly.

Consider:

```text
10,000 users
      ×
20 requests/day
      ×
30 days
      =
6,000,000 requests/month
```

Now add:

* Embedding calls
* LLM calls
* Re-ranking
* Tool calls
* Long contexts

Cost becomes an architecture concern.

Useful strategies include:

* Response caching
* Semantic caching
* Smaller models for simple tasks
* Token limits
* Context compression
* Retrieval optimization
* Request routing
* Batch processing where appropriate

---

# 10. Failure Handling

LLMs fail.

APIs fail.

Vector databases fail.

Enterprise systems fail.

Your application must expect that.

```text
LLM Timeout
    ↓
Retry
    ↓
Still Failed?
    ↓
Fallback Model
    ↓
Still Failed?
    ↓
Graceful Error
```

Similarly:

```text
Tool Failure
    ↓
Capture Error
    ↓
Retry / Alternative Tool
    ↓
Continue or Fail Gracefully
```

Never allow an AI failure to become an uncontrolled enterprise outage.

---

# 11. LangChain vs LangGraph

This distinction matters.

**LangChain** provides components and abstractions for building LLM applications.

**LangGraph** is designed for more stateful, controllable agent workflows.

A simple workflow might be:

```text
Question
 ↓
Retrieve
 ↓
Generate
 ↓
Answer
```

An agentic workflow might be:

```text
             ┌───────────────┐
             │     Agent     │
             └───────┬───────┘
                     ↓
                 Decide
              ↙     ↓     ↘
          Search   API    Database
              ↘     ↓     ↙
                 Evaluate
                     ↓
                  Decide
                     ↓
                  Answer
```

The more state, branching, tool usage, and control you need, the more important explicit workflow orchestration becomes.

---

# 12. What LangChain Should NOT Do

Don't put everything inside LangChain.

Your architecture should separate:

```text
Enterprise Application
        │
        ├── Security
        ├── Authentication
        ├── Business Logic
        ├── Data Access
        ├── Observability
        └── AI Orchestration
                    │
                 LangChain
                    │
          ┌─────────┼─────────┐
          ↓         ↓         ↓
        LLM      Retriever   Tools
```

LangChain is a component of the system.

It is **not the system itself**.
